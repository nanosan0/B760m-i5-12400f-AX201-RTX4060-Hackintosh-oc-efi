# v2.0.0 — Wi-Fi 换驱动，隔空投送可用

发布日期：2026-11-18

## 主要变化

| 项目 | v1.1.1 | v2.0.0 |
| --- | --- | --- |
| Wi-Fi 驱动 | `AirportItlwm` 2.4.0（laobamac，构建 `7204c69`） | **`ForbiddenItlwm` 0.6.0-beta.2**（Tahoe 构建） |
| 蓝牙 | `IntelBluetoothFirmware` 2.5.0 + `IntelBTPatcher` 2.5.0 | 同左，但 **`IntelBTPatcher` 停用**，由 `BTLEAdvFixup` 0.9.3 接管 |

| kext 数量 | 20 | 21（+`ForbiddenItlwm`、`BTLEAdvFixup`，−`AirportItlwm`） |

### 1. Wi-Fi 驱动换成 ForbiddenItlwm

`AirportItlwm` 2.4.0 在本机（AX201 / macOS 26.7.2 / 25G332）能连网，但**扫描请求会周期性超时**：`airportd` 报 `Completed scan (error=-3905)`，耗时固定 20.19 s，Wi-Fi 菜单里经常刷不出网络列表。

驱动侧自带的扫描计数器把原因指了出来：

```
ItlwmScanStats = "req=36 ok=20 notready=16 timeout=1 beacons=129"
```

`beacons` 在涨，说明电台听得到路由器；`timeout` 也在涨，说明**固件的扫描完成通知有时根本不回来**，是驱动自己的 20 秒看门狗兜的底。`notready` 则是 `iwx_stop` 清掉 `IFF_RUNNING` 后，接口被反复放倒又拉起。

`ForbiddenItlwm` 是 `AirportItlwm` **2.4.1** 的分支（原作者 laobamac 的上游修复它都带着），同时补齐了 AWDL 这条上游一直没做的链路。换过去之后：

```
scan_ms=9071 count=18          ← 9 秒扫到 18 个网络，不再固定 20 秒超时
```

> 版本对应：macOS 26.7.1 / 26.7.2 / 26.7.3 用 Tahoe 构建；`MinKernel` `25.0.0`、`MaxKernel` `25.99.99` 与 v1.1.1 的封顶策略一致。

### 2. 隔空投送：BTLEAdvFixup + 一整套启动参数

`ForbiddenItlwm` 的 AirDrop 默认是**关的**——不带任何 `-itlawdl*` 参数时，它的行为和 `AirportItlwm` 完全一样。要打开需要三样东西同时到位：

1. **`BTLEAdvFixup.kext` 0.9.3**：让 `bluetoothd` 能在 Intel 网卡上发起 BLE 广播。AirDrop 先用蓝牙 LE 找设备，没有它连发现阶段都过不去。
2. **整套 18 个启动参数**：少一个都可能表现为「别的设备列不出这台 Mac」或「能连上但极慢」。
3. **停用 `IntelBTPatcher.kext`**：它和 `BTLEAdvFixup` hook 同一个函数，两个插件同时在，Lilu 会直接 panic。

本机实测（重启后约 5 分钟，iPhone 在旁）：

| 指标 | 值 | 含义 |
| --- | --- | --- |
| `ItlwmAWDLBuildCheck` | `verified` | 25G332 在作者验证过的构建列表里 |
| `ItlwmAWDLMiState` | `on` | 服务宣告已发出，别的设备能知道这台 Mac 支持 AirDrop |
| `ItlwmAWDLSyncMIBuilt` | `1661` | 宣告帧在持续构建 |
| `ITLAWDLCoexAdded` | `Yes` | AWDL 监听器已建立 |
| `ITLAWDLCoexChannel` | `149` | 落在 5 GHz 的 AirDrop 信道（**不是 6**，6 会极慢） |
| `ITLAWDLCoexCountryLearned` | `Yes` | 固件已学到国家码 |
| `BTLEAdvHookRouted` | `1` | 蓝牙补丁命中并接管 |
| `ITLAWDLCoexPeerSyncFrames` | 785 → 824（8 秒） | 对端（iPhone）的同步帧正在被收到 |

`ifconfig awdl0` 也会出现一个独立接口：

```
awdl0: flags=8843<UP,BROADCAST,RUNNING,SIMPLEX,MULTICAST> mtu 1484
	ether 86:5b:41:b2:c1:a5
	inet6 fe80::845b:41ff:feb2:c1a5%awdl0
```

### 3. 关掉 `PowerTimeoutKernelPanic`（否则投送会卡在「等待」）

这一条和 AirDrop 无关，但会让 AirDrop 用不了。

macOS 26（Darwin 25.6）上，如果这一项是 `true`，OpenCore 会把内核里的字符串 `com.apple` 改写成 `not.apple`，而 **pf 的 anchor 校验共用这个字符串**，于是系统自带的 `/etc/pf.conf` 被当成用户自定义规则，pf 接管网络路径：

```
$ sysctl net.filter_state net.link.generic.system.enable_netagent
net.filter_state: pf                       ← 正常应为空
net.link.generic.system.enable_netagent: 0 ← 正常应为 1
```

结果是 macOS 关掉了自己的用户态网络路径，**AirDrop 的 QUIC 失去节奏控制**，表现为能发现设备、点发送一直等待或极慢。

改成 `false` 后 `net.filter_state` 为空、`net_agent` 为 1。

> 代价：这一项原本是防止「驱动切换电源状态太慢导致内核 panic」。本机（NullMoth 显卡驱动 + SimpleHDA）实测开关机与睡眠正常；若你的机器出现睡眠唤醒 panic，把它改回 `true`，并改用其他办法处理 pf（例如移除加载 anchor 的防火墙 App、或手动调整 `/etc/pf.conf`）。

## 升级注意

1. **必须整包替换**，不要只换 `config.plist`：本版删掉了 `AirportItlwm.kext`，新增 `ForbiddenItlwm.kext` 与 `BTLEAdvFixup.kext`。
2. **不要保留旧的 `AirportItlwm.kext`**，也不要同时启用它——两者都接管同一套 IO80211 虚表。
3. `boot-args` 必须是**完整的一组**，官方文档明确说明只加一部分会出现「其它设备完全列不出这台 Mac」。
4. `IntelBTPatcher.kext` 保持 `Enabled = false`（文件可以留着，方便回退）。
5. 三码仍是占位符，先用自己的 `MacPro7,1` 三码。
6. **升级 macOS 之前**：先去掉 `-btleadv`（或禁用 `BTLEAdvFixup`）启动一次再升级，因为增量更新会校验被 `bluetoothd` 打过补丁的页。

## 没有包含的东西

- **`-itllog`**：本仓库的 `boot-args` 不含这一项。它是诊断开关，会把驱动日志环发布到 ioreg，**任何 App 都能读到**（可能含网络名）。排障时临时加上即可，拿到数据后删掉。
- **AirDrop 相关的可选参数**（`itlwm_scanout`、`itlwm_lqmint`、`-itlawdlsta44`、`-itlawdlanybuild` 等）：保持默认，按需再加。其中 `-itlawdlanybuild` 会绕过构建校验，**有 panic 风险**，只在 U 盘上试。

## 回滚

| 目标 | 做法 |
| --- | --- |
| 回到 v1.1.1（有 Wi-Fi、无 AirDrop） | 换回 v1.1.1 的 `EFI` 目录 |
| 只关 AirDrop | 删掉 `-btleadv` 与全部 `-itlawdl*` 参数，禁用 `BTLEAdvFixup`，重新启用 `IntelBTPatcher` |
| 只回滚 pf 那一项 | `PowerTimeoutKernelPanic` 改回 `true` |

驱动本身不写磁盘：`ForbiddenItlwm` 只在内存里跑，`BTLEAdvFixup` 只对 `bluetoothd` 做内存补丁，卸载后无残留。
